# Сравнение технологий

## Назначение и статус

Документ подготовлен для дипломного проекта «Разработка интеллектуальной платформы поддержки персонализированного раннего вмешательства».

Статус: предварительное качественное сравнение. Предполагаемые функции включают анкеты, индивидуальные планы, рекомендации, разграничение доступа и историю результатов. Предметная область и требования требуют уточнения руководителя. Опыт участников с конкретными технологиями ещё необходимо подтвердить.

Характеристики технологий основаны на официальной документации. Выводы о применимости являются проектной оценкой. Замеры производительности и трудоёмкости не проводились.

## Критерии выбора

- Соответствие предполагаемым функциям платформы.
- Возможности интеграции пользовательского интерфейса, сервера и интеллектуального модуля.
- Работа с данными и контроль их корректности.
- Объём дополнительных компонентов и решений, необходимых команде.
- Подтверждённый опыт участников и возможность поддержки решения.

## 1. Серверные технологии

| Критерий | FastAPI | Django + Django REST Framework | NestJS |
| --- | --- | --- | --- |
| Язык и платформа | Python | Python | JavaScript / TypeScript, Node.js |
| Разработка API | Маршруты, модели запросов и автоматическая документация OpenAPI | API через сериализаторы, представления и маршрутизаторы DRF | Контроллеры, сервисы и модули; OpenAPI через дополнительный модуль |
| Проверка входных данных | Модели и аннотации типов | Сериализаторы и валидаторы DRF | Pipes и библиотеки валидации |
| Работа с базой данных | Библиотеку работы с БД выбирает команда | Встроенные ORM и миграции Django | Возможны различные библиотеки и ORM |
| Пользователи и администрирование | Хранение пользователей, права и административные функции необходимо спроектировать и реализовать | Django предоставляет систему пользователей, разрешений и административный интерфейс | Механизмы доступа и управление пользователями реализуются в рамках архитектуры приложения |
| Взаимодействие с Python-модулем персонализации | Возможен вызов Python-кода внутри приложения | Возможен вызов Python-кода внутри приложения | Для Python-модуля потребуется согласовать межпроцессное взаимодействие, например HTTP API |
| Необходимые знания | Python, модели данных, зависимости и выбранная библиотека БД | Django ORM, миграции, DRF и настройка разрешений | TypeScript, контроллеры, сервисы и внедрение зависимостей |
| Применимость к проекту | Кандидат для API и интеллектуального модуля на Python | Кандидат, если важны встроенное администрирование и управление данными | Кандидат, если команда предпочитает TypeScript для серверной разработки |

- [Django — ORM и административный интерфейс](https://docs.djangoproject.com/en/5.2/intro/overview/).
- [Django — аутентификация и разрешения](https://docs.djangoproject.com/en/5.2/topics/auth/default/).
- [Django REST Framework — возможности](https://www.django-rest-framework.org/).
- [NestJS — введение](https://docs.nestjs.com/).
- [NestJS — валидация](https://docs.nestjs.com/application/validation).
- [NestJS — работа с базами данных](https://docs.nestjs.com/techniques/database).
- [NestJS — OpenAPI](https://docs.nestjs.com/openapi/introduction).

Предварительный вывод: FastAPI рассматривается как основной кандидат при условии, что backend и интеллектуальный модуль будут разрабатываться на Python. Это позволит начать с одного серверного приложения. Если приоритетом станет управление каталогом заданий через готовый административный интерфейс, следует отдельно оценить Django + DRF. Если подтверждённый опыт backend-разработчика связан с TypeScript, необходимо повторно оценить NestJS и затраты на интеграцию Python-модуля.

## 2. Системы хранения данных

| Критерий | PostgreSQL | MySQL с InnoDB | MongoDB |
| --- | --- | --- | --- |
| Модель данных | Реляционная: таблицы и связи | Реляционная: таблицы и связи | Документная: документы с вложенными структурами |
| Связи между сущностями | Первичные и внешние ключи | Первичные и внешние ключи | Вложенные документы или ссылки между документами |
| Контроль целостности | Ограничения PRIMARY KEY, FOREIGN KEY, UNIQUE и CHECK | Ограничения целостности, включая внешние ключи InnoDB | Требует проектирования структуры документов, валидации и согласованности ссылок |
| Данные анкет переменной структуры | Типы json и jsonb | Тип JSON | Вложенные поля и массивы в документах |
| Транзакции | Поддерживаются | Поддерживаются в InnoDB | Поддерживаются; многодокументные транзакции требуют соответствующей конфигурации развёртывания |
| Применение к платформе | Пользователи, профили, планы, задания и результаты могут быть представлены связанными таблицами | Подходит для аналогичной реляционной структуры | Можно моделировать анкеты и другие данные документами; границы вложения и ссылок нужно обосновать |
| Основная работа при проектировании | Таблицы, связи, ограничения, индексы и миграции | Таблицы, связи, ограничения, индексы и миграции | Границы документов, выбор вложения или ссылок, обновление связанных сведений |

Источники:

- [PostgreSQL — ограничения целостности](https://www.postgresql.org/docs/current/ddl-constraints.html).
- [PostgreSQL — JSON](https://www.postgresql.org/docs/current/functions-json.html).
- [MySQL — InnoDB](https://dev.mysql.com/doc/refman/8.4/en/innodb-introduction.html).
- [MySQL — JSON](https://dev.mysql.com/doc/refman/8.4/en/json.html).
- [MongoDB — моделирование данных](https://www.mongodb.com/resources/basics/databases/data-modeling).
- [MongoDB — транзакции](https://www.mongodb.com/docs/manual/core/transactions/).

Предварительный вывод: предполагаемая структура проекта содержит связанные сущности, поэтому реляционная база представляется подходящим вариантом. PostgreSQL предлагается как кандидат, позволяющий сочетать связанные таблицы с JSON-данными при необходимости. MySQL остаётся полноценной альтернативой. Окончательный выбор между ними требует уточнения модели данных, опыта команды и условий размещения приложения. Преимущество по скорости или стоимости эксплуатации не установлено.

## 5. Предварительное решение и его проверка

Предварительно рассматривается стек FastAPI, PostgreSQL и React с TypeScript. Это предложение для обсуждения, а не утверждённое решение команды.

Основания: предполагаемая реализация интеллектуального модуля на Python, связанная структура данных и компонентная организация интерфейса. Эти основания требуют подтверждения.

Проверка предлагаемого стека:

1. Реализовать один сквозной сценарий: форма отправляет данные в API, сервер сохраняет их в БД и возвращает результат.
2. Проверить обработку некорректных входных данных.
3. Продемонстрировать взаимодействие сервера с заглушкой интеллектуального модуля.
4. Зафиксировать трудности интеграции и необходимые дополнительные компоненты.
5. После проверки и обсуждения принять решение либо скорректировать выбор.
