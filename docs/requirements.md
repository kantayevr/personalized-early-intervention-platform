# Требования к платформе и критерии приёмки

## 1. Назначение и статус

Проект: «Разработка интеллектуальной платформы поддержки персонализированного раннего вмешательства».

Документ содержит первоначальные функциональные и нефункциональные требования к дипломному прототипу. Ответственный за подготовку: Кантаев Рамазан Болатович. Проверка проводится совместно с Нагумашем Дауреном Болатовичем и Каманом Алишером Аймуратулы.

Статус: черновик для обсуждения. Предполагаемая предметная область — ранняя помощь детям при взаимодействии специалиста с родителем или законным представителем. Это предположение основано на списке соседних дипломных тем; ответ руководителя ещё требуется. Возраст детей, направление помощи, содержание анкет и рекомендаций не утверждены.

В этой версии нет ссылок на проведённые интервью или подтверждённые запросы заказчика. Бизнес-требования обозначены как предположения. Числовые показатели качества являются предложенными целями проверки, а не измеренными результатами.

Связанная задача YouTrack: [DIP-6 — Specify requirements and acceptance criteria](https://kantayevr.youtrack.cloud/issue/DIP-6).

## 2. Основания и приоритеты

| Код основания | Содержание | Статус |
| --- | --- | --- |
| SRC-1 | Предварительное описание проекта: профиль, анкета, рекомендации, утверждение плана и история результатов | Рабочая концепция; требует согласования руководителя и проверки потребностей |
| SRC-2 | Проектное предложение автора документа по доступу, целостности данных и удобству прототипа | Предлагается для проверки командой |
| SRC-3 | Требования к этапу сдачи: наличие проверяемых требований, архитектуры, прототипа и плана оценки | Основано на полученном задании к 24 октября; не подтверждает конкретные бизнес-функции |

Для каждого требования указан приоритет:

- Must — предлагаемый обязательный объём дипломного прототипа после согласования.
- Should — желательно реализовать после основных сценариев.
- Could — дополнительная возможность при наличии времени.

Статус всех требований в этой версии — «Предлагается». Приоритет Must не означает, что требование уже согласовано пользователями или реализовано. После обсуждений необходимо добавить ссылки на подтверждающие материалы, записать решения и пересмотреть приоритеты.

## 3. Роли и границы доступа

| Роль | Предлагаемые действия | Границы доступа |
| --- | --- | --- |
| Родитель или законный представитель | Регистрация, работа с доступными профилями, заполнение анкеты, просмотр опубликованного плана, внесение результатов | Только профили, к которым явно предоставлен доступ; утверждение рекомендаций недоступно |
| Специалист | Просмотр назначенных профилей, добавление наблюдений, запрос рекомендаций, подготовка и публикация плана | Только назначенные профили; права администратора не предоставляются автоматически |
| Администратор прототипа | Создание учётных записей специалистов, назначение ролей и связей доступа, подготовка каталога | Административные операции; действия фиксируются в журнале |

Для прототипа административные операции могут выполняться предусмотренными серверными средствами или скриптом подготовки данных. Отдельный административный веб-интерфейс имеет приоритет Should.

Один профиль в демонстрационном сценарии связан с одним родителем и одним специалистом. Необходимость нескольких родителей или специалистов на профиль уточняется отдельно.

## 4. Основной сценарий

1. Родитель входит в систему, создаёт профиль и заполняет анкету.
2. Администратор предоставляет специалисту доступ к профилю.
3. Специалист просматривает данные и при необходимости добавляет наблюдение.
4. Интеллектуальный модуль предлагает подходящие задания из подготовленного каталога и объясняет подбор.
5. Специалист проверяет, изменяет и публикует индивидуальный план.
6. Родитель просматривает опубликованные задания и фиксирует результаты.
7. Специалист и родитель просматривают выполнение плана; специалист при необходимости создаёт новую версию.

Этот сценарий описывает предполагаемый прототип. Его востребованность и детали подлежат проверке в рамках исследования пользователей.

Критерии ниже проверяются на учебных данных. Проверяемые примеры заданий и правил подбора должны входить в тестовые материалы.

| FR-08 | Подбор использует каталог заданий с идентификаторами и условиями применимости | Must | SRC-1, SRC-2 | Все предложенные задания существуют в зафиксированной версии каталога; исключённые из доступного подбора задания не попадают в новые предложения; для демонстрации достаточно заранее подготовленного каталога |

| FR-11 | Система сообщает о недостаточности данных для подбора | Must | SRC-1, SRC-2 | Если отсутствуют данные, обязательные для выбранных правил, система перечисляет недостающие сведения и не выдаёт неподтверждённый план как готовую рекомендацию |

| FR-16 | Система отображает выполнение плана | Must | SRC-1 | Отображаются общее количество пунктов, число выполненных, пропущенных и оставшихся; процент рассчитывается по формуле раздела 7 и совпадает с сохранёнными результатами |

### Уточнения к функциональным требованиям

- Содержание анкет, возрастные диапазоны, направления поддержки и критерии применимости заданий должны быть согласованы с руководителем и специалистом предметной области. В прототипе используются явно обозначенные учебные примеры.
- Регистрация специалистов через открытый выбор привилегированной роли не предусмотрена. Отправка приглашений и восстановление доступа по электронной почте не входят в обязательный объём этой версии.
- Пункт плана соответствует одному назначенному выполнению. Если задание назначается повторно, создаётся отдельный пункт. В обязательном объёме итог пункта сохраняется один раз; необходимость исправления результата с историей изменений уточняется отдельно.
- История версий не требует отдельной распределённой системы: важны сохранность данных и проверяемое поведение.
- Для первой версии допустим подбор по правилам. Обучение ML-модели не является условием выполнения FR-09; выбранный метод и его ограничения должны быть описаны отдельно.

## 7. Определения данных и показателей

### Основные объекты

| Объект | Минимальное назначение |
| --- | --- |
| Учётная запись | Идентификатор пользователя, данные входа и роль |
| Профиль | Учебное обозначение ребёнка, необходимые для согласованных правил признаки и связи доступа |
| Анкета | Версия структуры, ответы, профиль и время сохранения |
| Наблюдение | Запись специалиста с автором и временем |
| Каталог | Версия заданий, тексты и формализованные условия применимости |
| Предложение рекомендаций | Подобранные задания, объяснения, ссылки на версии входных данных, каталога и алгоритма |
| Версия плана | Зафиксированный набор пунктов, статус, автор и время публикации |
| Пункт плана | Одно назначенное выполнение задания с сохранённой инструкцией |
| Результат | Связь с пунктом плана, итог, необязательный комментарий, автор и время |

Это концептуальный перечень, а не утверждённая схема БД. Состав полей и связей уточняется при проектировании.

### Выполнение плана

- N — количество пунктов выбранной опубликованной версии плана.
- C — количество пунктов с результатом «выполнено».
- S — количество пунктов с результатом «пропущено».
- R = N - C - S — количество пунктов без результата.
- При N > 0 процент выполнения = 100 × C / N, округление до одного знака после запятой.
- При N = 0 отображается «Нет назначенных заданий»; деление на ноль не выполняется.

Пример проверки: для пяти пунктов, из которых два выполнены и один пропущен, система показывает N = 5, C = 2, S = 1, R = 2, выполнение 40,0%.

Эти показатели отражают выполнение заданий. Оценка развития ребёнка и профессиональная интерпретация результатов требуют отдельных согласованных методик и не выводятся из процента выполнения.

Проверки здесь запланированы. Документ не подтверждает, что они уже выполнены. На начальном этапе сдачи представляются спецификация и план проверки; полностью готовое приложение не требуется. Готовность документа требований и выполнение требований будущим приложением оцениваются отдельно. Для последующей приёмки согласованного Must-требования необходимо приложить фактическое свидетельство выполнения и зафиксировать выявленные ограничения.

## 9. Границы текущего прототипа

Предлагаемый объём включает один веб-интерфейс, серверное API, хранение данных и модуль персонализации. Выделение интеллектуального модуля в отдельный сервис не является обязательным требованием.

В обязательный объём не включены:

- постановка диагнозов, назначение лечения и доказательство клинической эффективности;
- обучение модели на реальных данных детей;
- интеграция с медицинскими или государственными системами;
- мобильные приложения для отдельных платформ;
- платежи, видеосвязь и внешние уведомления;
- автоматическая публикация рекомендаций без проверки специалистом.
